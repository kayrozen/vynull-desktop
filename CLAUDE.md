System packages (Debian and Ubuntu names; installed on this machine): `libwebkit2gtk-4.1-dev libgtk-3-dev libxdo-dev libasound2-dev`. Workspace tests: `cargo test --workspace` (98 pass, 9 are ignored because they need a daemon or a sound card; see below), then `ui-tests/run.sh` (346 browser checks, the same in Firefox and in Chrome (library.mjs also run in Chrome after the last change)).

`vynull-api` has the serde types for status, players, now-playing, the SSE `StateEvent`, peers, history, tracks, metadata patch, cues, analysis, tags, playlists and acks (`src/types.rs`). Optional fields use `#[serde(default)]` and Go's `null` lists go through `null_default`. `src/client.rs` is a reqwest `Client` (native and wasm32) covering every endpoint in the 0.6.0 spec except SSE (see `vynull-platform`), `GET /api/audio`, artwork/waveform-PNG bodies (URL helpers only), `/api/analysis/ext/...`, `/api/tracks/add*` and `/api/tracks/reimport`. Reads return typed structs; writes that only ack return `()` (the `ok`/`OK` spelling is never inspected). Settings `full` stays an untyped `serde_json::Value`. Contract tests: `ci/run-contract-tests.sh` (needs `VYNULL_BIN`, ffmpeg, python3, curl) generates a synthetic fixture library (`ci/make-fixtures.sh`: a 120 BPM click WAV, a 128 BPM MP3, an AIFF and an accented FLAC; no real music), starts a daemon on `127.0.0.1:19443` with a throwaway data dir, and runs all `#[ignore]` tests with `VYNULL_FIXTURE=1`, which turns on the tests that write data (metadata, color, rating, cues, tags, playlists, beat-grid adjust), audio Range and `X-Audio-Source` checks, and analysis checks (the click track must analyze at 120 BPM). On a machine where a real daemon already holds the Pro DJ Link ports (UDP 50000, NFS 2049, ...) the fixture daemon cannot start; run `VYNULL_BIN=/home/kay/vynull/vynull ISOLATE=1 ci/run-contract-tests.sh`, which uses a private network namespace (`unshare -rn`). The same tests run read-only against any daemon with `VYNULL_URL=http://127.0.0.1:9443 cargo test --workspace -- --ignored` (needs `curl`); the fixture tests skip themselves without `VYNULL_FIXTURE`. Daemon quirk found by these tests: `PUT /api/tracks/{id}/metadata` replies with `"duration":0.000` (a float; the list sends an integer), so `TrackInfo.duration` accepts both. Live check, as above: `VYNULL_URL=http://127.0.0.1:9443 cargo test --workspace -- --ignored` (read-only, needs `curl`). The local daemon must be built from the current checkout: a binary from before commit `1ad1dc6` (Oct 10) has no `/api/events` and no uniform CORS, and `live_daemon_opens` fails with a 404.

`vynull-platform::events::state_stream(url)` is the SSE stream (`StreamItem::{Open, State, Error}`), with a web backend (`EventSource`, browser auto-reconnect) and a native one (`eventsource-stream`, reconnect with 0.5-5 s backoff). The native one is tested against a fake SSE server; the web one only compiles (no wasm-bindgen-test yet). `vynull-platform::store` has the `Store` trait (sync string get/set/remove, no `Send`/`Sync` bound), `StoreExt` (JSON helpers, also on `dyn Store`), `MemoryStore`, `FileStore` (native: one JSON file under the OS config dir, atomic writes, a corrupt file is moved to `.corrupt` and the store starts empty) and `WebStore` (localStorage, keys prefixed `vynull.`, falls back to `MemoryStore` when blocked). `FileStore` is tested; `WebStore` only compiles. The key names and value structs (search history, column layout, and so on) are not defined yet; they belong with the UI. `vynull-platform::audio` has the `AudioPlayer` trait (`load`, `play`, `pause`, `seek`, `set_volume`, `state`, `click_at`), polled by the UI like the SSE stream: errors surface as `PlayStatus::Failed`, not return values. The metronome has no scheduler in the platform crate: the UI looks ahead from `state().position_secs` and the beat grid and calls `click_at(delay, accent)` so clicks use the audio clock. `FakeAudio` (scripted time) is tested; `WebAudio` (`HtmlAudioElement` + WebAudio oscillator clicks) only compiles and has never run in a browser. `NativeAudio` (native only, `audio/native.rs`) fetches the track over HTTP in a thread, decodes it whole with symphonia 0.5 (mp3, FLAC, WAV, Ogg Vorbis: what the daemon serves directly; it converts the rest to WAV) and mixes it in the sound card's callback with cpal 0.18, resampling by linear interpolation and mixing metronome clicks on the output clock. The mixer (`audio/native/engine.rs`) is pure and has unit tests; `plays_through_the_sound_card` (ignored by default, run it with `cargo test -p vynull-platform --lib -- --ignored plays_through`) opened the default ALSA device here, played a quiet 440 Hz tone, held the playhead on pause, seeked and reached the end. Whole-file decoding costs memory (about 60 MB for 6 minutes of 44.1 kHz stereo) and a moment on load; there is no streaming. symphonia is pinned to 0.5: 0.6 changed its API. `Client::audio_url_transcoded` gives the `?transcode=1` URL.

`spike/` is the throwaway phase 0 Dioxus 0.7.10 spike (4,000-row virtual list, one waveform moved by CSS transform, rAF fps meter). It is excluded from the workspace and has its own lockfile. Build with `cd spike && dx build --release --platform web` (or `dx serve` for dev); `dx` 0.7.10 is installed with `cargo install dioxus-cli --version 0.7.10 --locked`, which needs `libssl-dev`, and `dx` downloads `wasm-opt` on first use. The output is under `spike/target/dx/vynull-spike/release/web/public`; serve it statically. Query params: `?api=http://host:9443&n=4000&scroll=1&wave=1`; it needs the daemon for real data. Numbers are mirrored to `window.__spike`. Results so far (headless Firefox 157 on a 20-thread x86 desktop, daemon library padded from 1123 to 4000 rows): a steady 60 fps (p95 17.3 ms) in idle, auto-scroll, waveform, and both together, also when pinned to one core with `taskset -c 0`; first row after about 200 ms (about 500 ms on one core); the `dx` release bundle gives the same numbers, with a 2.36 MB wasm (624 KB gzipped); a plain `wasm-bindgen` build without `wasm-opt` was 1.5 MB (443 KB gzipped), so `dx`'s default release profile is not size-tuned and needs a look before shipping. Weak-CPU proxy (no ARM board available; `systemd-run --user --scope -p CPUQuota=N% taskset -c 0 firefox`, which caps the whole browser, so it is pessimistic): at 25% of a core, idle 59 fps, auto-scroll 15.7 fps (p95 101 ms), waveform 42 fps, scroll+waveform 38 fps, first row after about 2 s; at 12%, 7-11 fps everywhere and first row after about 10 s. Scrolling is the weak path (each scroll event re-renders the visible rows). This does not pass the 30 fps exit test at 25%, and it is not a real ARM result. iPhone 11 (Safari, A13, reported by the user, presumably with `scroll=1&wave=1`): 60.5 fps, p95 18.0 ms, worst 19.0 ms. That is real ARM and real WebKit, but a far faster core than a Pi, so it does not test the low-power case. Not yet measured: Chrome, a low-power ARM device, the SSE-driven updates, and a sorted or filtered list. The canvas holds the whole track at 75 px/s, so a 10-minute track is 47,625 px wide, past Firefox's 32,767 px limit, so the real waveform must be windowed or tiled.

Tags, Settings, Diag and Overlay screens (`tags.rs`, `settings.rs`, `diag.rs`, `overlay.rs` in `vynull-ui/src`; their logic is in `vynull-core::{diag, settings, overlay}` with unit tests):

Deleting a tag or a category takes two clicks. A tag's dot uses its palette color when it has one and a hue from its id otherwise (`palette::tag_color`; the daemon's tags have no color in practice). A new tag starts in the selected tag's category, or the first one, and creation is refused with a message when there is no category yet.
- Settings, seven sections as in the mockup. WEB UI: theme (night or day) and row density (comfort or compact), and the three waveform band colors with presets and a preview; all kept in the store (`look`, `wave` keys), applied at once through `LookCtx`, and used by the Players overview and the drawer but not by the library's row waveforms (those are the daemon's PNGs). LIBRARY SOURCE: the analysis BPM range (60 to 200, at least 10 apart, applied on blur or Enter), replace a path prefix, re-import tags (asks first). The mockup's link mode, network interface, music folder and lazy-analysis rows are not in the API (they are daemon start-up options), so they are not shown and a note says why. Routing, fonts and `eval`: the screen is in the URL hash (`#/library/playlist/5/track/123`, `#/library/queue`, `#/library/history`, `#/players`, ...; `vynull-core::route`, `vynull-ui/src/nav.rs`). Fonts (Roboto Latin and Latin Extended, Cousine 400 and 700 Latin; Apache-2.0, see `crates/vynull-ui/assets/fonts/README.md`) are embedded as data URLs by `fonts.rs`, so nothing is fetched from outside (tested: no request leaves the app and the daemon); other scripts fall back to system fonts. Daemon behavior found while building the drawer (fixture daemon, v0.6.0), which differs from what the mockup or the spec suggest: (1) `PUT /api/tracks/{id}/beats {bpm}` rebuilds the grid from the first beat and does not keep the downbeat; the client changes the tempo with `POST /api/analysis/beatgrid/adjust {bpm, set_downbeat_ms}` using the first bar line's time. (2) After that adjust, `GET /api/tracks/{id}/beats` still reports the old bpm and `detected_bpm` 0; only `GET /api/analysis/{id}` (and the library list) show the new tempo, so the drawer reads the tempo from the analysis. (3) `beat_phase_shift` renumbers `beat_in_bar` (which beat starts a bar) and moves no beat times. (4) `PUT .../beats {clear:true}` resets the summary but leaves the old beat list in `/api/analysis/{id}` until `POST /api/analysis/reanalyze/{id}`, so CLEAR does both. (5) The daemon omits `color_id` from a track when it is 0. (6) The fixture daemon analyzes a track only when asked: library durations and BPMs stay 0 until `/api/analysis/{id}` is called.

## What this project is

A Rust client for the Vynull 0.6.0 HTTP API (a DJ/library daemon, default `127.0.0.1:9443`). One Cargo workspace of six crates should produce the web client (wasm32) and the desktop clients from the same code. The UI and core crates hold no platform code. A platform layer holds the web and native backends.

Planned stack: Dioxus UI (egui is the fallback, to be decided after the phase 0 spike), reqwest for HTTP, SSE for live state (`EventSource` via web-sys on web, `eventsource-stream` on native), hand-written serde types from `openapi.yaml`, and a `Store` trait (localStorage on web, config file on native). Audio goes behind a trait (HTMLAudioElement/WebAudio on web, symphonia + cpal on native). Build with `dx`, trunk as the web fallback. Client is MIT licensed.

## API constraints that shape the code

- No authentication. Keep the client LAN-only, store no secrets, and warn when the host is not private.
- `GET /api/events` is an SSE stream (~4 Hz). Interpolate the playhead between events with `beat_age_ms`.
- `GET /api/tracks` returns the whole library (~4,000 tracks) in one array, with ETag. Use `/api/tracks/rev`, keep the parsed library in memory, virtualize the list, and run search client-side (accent-insensitive, AND between words).
- The API exposes no mixer fader levels or crossfader. The `mixer` object has only `master_device`, `master_bpm` and `channel_on_air`. The Players screen shows on-air state only, never faders (decided).
- The spec has quirks, for example both `OK` and `ok` ack keys. Handle both in the typed client.
- The status endpoint has no version field, so contract tests against a real 0.6.0 daemon are the drift check.
- When BPM changes, keep the downbeat by sending `bpm` plus `set_downbeat_ms` to `POST /api/analysis/beatgrid/adjust` (not `PUT /api/tracks/{id}/beats`, which only takes `bpm`, `beat_phase_shift`, `clear`).
- CORS allows only the `Content-Type` request header and exposes no response headers. Cross-origin, a browser cannot send `If-None-Match` or read `ETag` or `X-Audio-Source`. Those work only same-origin (`/app`) or natively, so detect library changes with `/api/tracks/rev`.
- Error statuses: a negative track ID gives 400, an unknown ID gives 404, both as `text/plain`.
- Read the `X-Audio-Source` header on `/api/audio/{id}` for the DIRECT or TRANSCODED label.
- Client-only persisted data (the API cannot hold it): search history, column layout, color history, waveform colors, theme, row density, volume, metronome state.
- A hosted HTTPS page cannot call the HTTP daemon. The web bundle is meant to be served by the daemon itself at `/app` (a planned `--app-dir` flag in the Vynull repo).
